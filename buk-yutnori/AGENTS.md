# AGENTS.md

## 1. 역할

이 저장소에서 작업하는 에이전트는 `docs/`와 `spec/`를 요구사항의 정본으로 취급한다. 규칙을 추측하여 보완하거나, 일반적인 윷놀이 규칙으로 조용히 대체하지 않는다.

## 2. 절대 규칙

- 서버가 모든 난수, 이동 유효성, 턴, 승패를 판정한다.
- 클라이언트 상태는 표시용이며 정본이 아니다.
- 게임 규칙 엔진은 UI·네트워크·DB와 분리된 순수 도메인 모듈이어야 한다.
- 구현 중 명세 충돌이나 빈칸을 발견하면 `docs/12_open_items.md`에 기록한다.
- 콘텐츠 규칙을 변경하려면 코드보다 명세와 테스트를 먼저 수정한다.
- 이미 서버에서 확정된 이벤트를 클라이언트 애니메이션 때문에 롤백하지 않는다.
- 중복 명령은 `command_id`로 멱등 처리한다.
- 진행 중 경기 이벤트는 감사 로그로 저장하지만, v1은 서버 재시작 후 경기를 복구하지 않는다.
- 운영 환경은 HTTPS/WSS를 전제로 한다.
- 전체 윷판 구조는 `spec/board_graph.yaml`을 정본으로 사용하며 다른 판 구조로 임의 변경하지 않는다.

## 3. 구현 원칙

- Go 서버와 raylib/WASM 클라이언트의 경계는 명시적 프로토콜로 유지한다.
- v1 메시지 형식의 기본값은 JSON이다. 벤치마크로 필요성이 입증되기 전까지 바이너리 프로토콜로 선행 최적화하지 않는다.
- 게임 WebSocket은 하나의 연결 안에서 `type`, `request_id`, `command_id`, `sequence`, `payload`로 메시지를 구분한다.
- 인증·프로필·방 목록·방 생성 같은 요청/응답 API는 HTTP를 사용한다.
- 방 상태, 경기 명령, 경기 이벤트, 채팅, 관전, 재접속 동기화는 WebSocket을 사용한다.
- 세션 식별자를 사용자 ID로 사용하지 않는다.
- 브라우저의 30일 로그인 유지는 Secure/HttpOnly/SameSite 쿠키로 구현한다.
- 테스트 모드에서 난수 시드 고정을 지원한다.

## 4. 작업 절차

1. 관련 명세와 스키마를 읽는다.
2. 변경하려는 불변조건을 테스트로 작성한다.
3. 최소 구현을 작성한다.
4. 단위 테스트와 통합 테스트를 실행한다.
5. 명세에서 벗어난 기술 결정을 ADR로 남긴다.
6. 한 PR에는 하나의 명확한 기능 또는 위험 영역만 포함한다.
7. `docs/development/git-workflow.md`의 브랜치·리뷰·병합 정책을 따른다.

## 5. Git과 리뷰

- GitHub Flow와 기본 브랜치 `main`을 사용한다.
- 기능·버그·테스트·리팩터링·스파이크 및 고위험 변경은 Issue가 필수다.
- Milestone 0~1은 외부 승인 0명이지만 자기 검토, Codex 자체 리뷰와 필수 CI를 생략하지 않는다.
- Milestone 2부터 고위험 변경은 사람, 별도 에이전트 세션 또는 외부 모델의 독립 리뷰 1회를 요구한다.
- 게임 규칙의 의미 변경은 항상 사용자 승인을 먼저 받는다.
- docs-only 여부는 경로가 아니라 의미 변화로 판단한다.
- bootstrap 종료 뒤 `main` 직접 push와 force push를 금지한다.
- squash merge만 사용하고 병합 뒤 브랜치를 삭제한다.

## 7. 코드 리뷰 중점

- 큐 처리 순서가 명세와 일치하는가
- 북이 일반 이동값으로 취급되지 않는가
- 북 앞의 결과가 먼저 처리되는가
- 업기 불가 상태에서 동일 칸의 여러 말이 독립 상태를 유지하는가
- 상대가 도착하면 대상 칸의 상대 말을 모두 잡는가
- 시간 초과 CPU 대체가 해당 턴에만 적용되는가
- 재접속 시 이미 확정된 행동을 롤백하지 않는가
- 전원 이탈 30초 유예와 방 폐쇄가 원자적으로 처리되는가
- 준비 완료 상태에서 팀·상세 설정 변경이 차단되는가
