# 인증, 세션, 프로필, 전적

## Google 로그인

1. 브라우저가 Google 로그인 수행
2. Google ID 토큰을 서버로 전달
3. 서버가 토큰 검증
4. Google `sub`를 외부 계정 식별자로 저장
5. 내부 사용자 ID를 별도로 유지
6. 서버 자체 세션 생성

Google 토큰을 게임 세션이나 사용자 ID로 직접 사용하지 않는다.
브라우저 callback이 받은 ID 토큰은 같은 origin의 JSON API로 한 번 전달하고,
서버는 Google의 서명·audience·issuer·만료 검증이 끝난 `sub`만 계정 연결에
사용한다. 이메일과 표시 이름은 외부 계정 식별자로 사용하지 않는다.

## 30일 세션

- 로그인 유지 목표: 30일
- 브라우저 저장: `Secure`, `HttpOnly`, `SameSite` 쿠키
- DB 저장:
  - 세션 ID 또는 토큰 해시
  - 사용자 ID
  - 생성일
  - 만료일
  - 마지막 사용일
  - 폐기 여부
- 운영 환경 HTTPS 필수
- 세션 원문을 DB에 저장하지 않는다.
- 세션 원문은 256-bit 서버 난수로 생성하고 저장소에는 SHA-256 digest만 전달한다.
- 내부 사용자 ID는 Google `sub` 및 세션 식별자와 별도로 생성한다.
- 쿠키 이름은 `__Host-buk_session`, `Path=/`, Domain 없음,
  `SameSite=Strict`로 고정한다.
- 만료는 생성 시점부터 절대 30일이며 마지막 사용으로 연장하지 않는다.
- 로그아웃은 저장 세션을 폐기하고 브라우저 쿠키를 제거한다.
- SQLite의 만료 세션 행은 인증 거부와 별개로 서버 시작 직후 및 매시간 정리한다.
  정리는 `expires_at <= 현재 시각`인 행만 만료 시각 순서의 제한된 batch로 삭제하며,
  아직 유효한 세션과 연결된 사용자·profile·전적 행은 삭제하지 않는다. 폐기 세션도
  원래 절대 만료 시각까지 폐기 기록을 유지한 뒤 같은 정리 대상에 포함한다.
- 세션 정리의 일시적 저장소 오류는 인증 서버를 중단시키지 않고 기록한 뒤 다음 주기에
  재시도한다. 서버 종료 시 정리 worker도 같은 shutdown context로 종료한다.
- WebSocket handshake도 같은 쿠키를 서버에서 검증한다. 브라우저가 세션 원문이나
  사용자 ID를 메시지 또는 query parameter로 복제하지 않는다.

서버는 SQLite 정본 저장소가 `auth.Store`도 구현하게 하여 계정과 세션을 같은 로컬
DB에 영구 저장한다. 재시작 뒤에도 유효·미폐기 session digest는 기존 내부 사용자
ID로 인증되며, 마지막 사용 시각만 갱신하고 최초 생성 시각 기준의 절대 30일 만료는
연장하지 않는다. `MemoryStore`는 단위 테스트와 수직 프로토타입용 어댑터로만
유지한다. 세부 경계는 `docs/adr/0005_http_google_auth_session_boundary.md`를 따른다.

## 닉네임

- 최초 로그인 시 별도 설정
- 변경 가능
- 변경 주기 제한 없음
- 중복 불가
- 비속어 금칙어 목록은 v1 미지원
- 2~20 Unicode extended grapheme cluster
- UTF-8이어야 하며 제어문자를 포함할 수 없음
- 앞뒤 공백은 허용하지 않음. 중간 공백은 허용함
- 중복은 저장된 UTF-8 문자열의 정확한 일치로 판정함. v1은 Unicode case folding이나
  normalization을 적용하지 않음

## 프로필

표시 항목:

- 닉네임
- 승리 수
- 패배 수
- 공개 프로필 여부

비공개 프로필은 닉네임만 보이고 승패를 숨긴다.

인증된 사용자는 `GET`/`PUT /api/v1/profile/me`로 본인 profile을 조회·설정한다.
`PUT`은 `X-Buk-Request: 1` JSON 요청만 받는다. `GET /api/v1/profiles/{user_id}`는
공개 profile을 조회하며, profile이 비공개여도 닉네임만 반환한다. profile HTTP
payload는 `schemas/http_profiles.schema.json`을 따른다.

인증된 전체 채팅, member-only room detail, 진행 중 경기의
`game_snapshot.participants[].nickname`은 서버가 응답/event 확정 시점에 profile에서
해석한다. profile이 아직 없거나 읽기 실패·손상 record면 동작을 막지 않고 안정적인 내부
`user_id`를 표시명으로 사용한다.

## 전적

- 정상 경기는 팀 최종 결과를 모든 팀원에게 적용
- CPU가 일부 또는 전부 대체해도 정상 전적으로 포함
- 중도 이탈자도 팀 최종 결과 적용
- 대기실에서 방장이 추가한 독립 CPU 플레이어는 계정이 아니므로 승·패 대상에서 제외
- 이탈 횟수는 내부 기록
- 무효 경기는 승패에 포함하지 않고 내부 기록만 저장
- 서버 오류, 서버 재시작, 전원 30초 이탈은 무효 경기

## 저장 데이터

영구 저장 대상:

- 사용자 계정
- Google `sub`
- 닉네임
- 공개 프로필 여부
- 승·패
- 세션
- 경기 결과
- 모든 경기 이벤트
- 채팅 기록
- 접속 및 이탈 기록
- 관리자 조치 기록

`profiles` 행은 `users.user_id`에 1:1로 연결되며 nickname과 공개 여부를 저장한다.
최초 profile 설정 전에는 행을 만들지 않는다. `user_stats` 행은 nickname과 독립적으로
사용자 ID에 1:1로 연결되어 승·패를 저장하며, 아직 profile을 설정하지 않은 경기
참가자도 정상 전적을 잃지 않는다. profile 조회는 두 행을 결합해 승·패를 반환한다.
경기 종료 이벤트와 전적 갱신은 같은 match-runtime transaction으로 확정한다.

## 게임 로그 조회

- 게임 로그는 `room_events`의 확정된 typed event에서 조회할 때 파생한다. 종료 시점의
  별도 기보 복사본이나 조회 전용 인덱스는 만들지 않는다(ADR-0014).
- 인증된 **현재 방 멤버**는 `GET /api/v1/rooms/{room_id}/game-logs`로 그 방의 종료된
  경기만 조회할 수 있다. 방이 삭제된 뒤의 역사적 조회 권한은 보존 기간·공개 범위와
  함께 별도 제품 정책으로 남긴다.
- 응답은 경기별 `match_id`, 시작·종료 sequence, 종료 상태와 사유, 정상 종료의 승리
  팀 및 sequence 순서의 기보 항목을 포함한다. 진행 중 경기는 응답에 포함하지 않는다.
- 기보 항목은 `YUT_RESULT`를 `{도}`·`{개}`·`{걸}`·`{윷}`·`{모}`·`{빽도}`·`{북}`으로,
  `PIECE_MOVED`를 각 말마다 `{[말 ID][이동 전 위치][이동 후 위치]}`으로 적는 안정적인
  사람이 읽는 파생 표현이다. 시작 전·완주 뒤 위치는 `-`으로 표시한다.
- 저장된 event payload가 해당 v1 wire 계약으로 읽히지 않으면 부분 로그를 추측하지
  않고 조회 전체를 서버 오류로 처리한다.

진행 중 경기 이벤트를 저장하더라도 v1은 이를 복구에 사용하지 않는다.

## v1 데이터베이스

- v1 정본 데이터베이스는 SQLite다.
- 단일 Go 서버와 같은 호스트의 로컬 영구 볼륨에서 사용한다.
- 네트워크 파일 시스템 위에 SQLite 파일을 두지 않는다.
- WAL 모드와 내구성 우선 동기화 설정을 사용하며, 경기 상태 변경 쓰기는 하나의 직렬화된 쓰기 경로로 보낸다.
- 트랜잭션은 짧게 유지하고 외부 네트워크 호출을 트랜잭션 안에서 수행하지 않는다.
- WAL 사용 중 백업은 SQLite 백업 API 또는 검증된 체크포인트 절차를 사용한다. DB 본체 파일만 임의 복사하지 않는다.
- DB 접근 경계는 PostgreSQL로 교체할 수 있도록 도메인 및 네트워크 계층과 분리한다.

SQLite 선택과 전환 조건은 `docs/adr/0001_sqlite_v1_and_scale_out.md`를 따른다.

## 경기 이벤트 확정과 저장 실패

- 경기 상태 변경 명령은 서버에서 먼저 검증하고 다음 상태와 이벤트를 계산한다.
- 해당 이벤트를 DB에 저장하는 데 성공한 뒤에만 서버 메모리 상태, sequence 및 외부 전송을 확정한다.
- 최초 저장 실패 시 경기를 자동 정지하고 활성 타이머를 보존한다.
- 최초 시도와 별도로 1초, 2초, 5초 간격으로 최대 3회 재시도한다.
- 자동 정지 중 새 경기 상태 변경 명령은 큐에 쌓지 않고 재시도 가능한 저장 장애 응답으로 거부한다.
- 3회 재시도 후에도 실패하면 경기를 무효 처리하고 클라이언트에 종료 사유를 알린다.
- DB 장애 때문에 무효 이벤트 자체를 저장할 수 없으면 메모리에서 무효 상태를 확정하고 구조화된 비상 로그를 남긴 뒤 DB 기록을 최선 노력으로 재시도한다. 이는 “DB 저장 후 경기 상태 확정” 원칙의 유일한 장애 종료 예외다.
- 채팅 로그 저장 실패는 채팅 전달이나 경기를 중단하지 않는다. 실패를 지표와 구조화 로그에 남기고 비동기 최선 노력 재시도를 허용하며, 끝내 저장되지 않을 수 있다.
