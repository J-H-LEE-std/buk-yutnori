# ADR-0014: 경기 이벤트 저장 방식과 인덱스

- 상태: 채택
- 결정일: 2026-08-22

## 맥락

`docs/12_open_items.md`의 구현 전 ADR 항목 "이벤트 저장 방식과 인덱스"를 해소한다.
비교 대상은 세 가지다.

1. 방 sequence별 typed event와 구조화된 payload를 정본으로 저장하고 기보는 여기서 파생
2. 턴 또는 경기 단위의 압축 기보를 정본으로 저장
3. typed event를 정본으로 유지하면서 종료 시 조회용 압축 기보를 함께 생성

평가보다 먼저 정본이 확정해 둔 제약이 있다.

- 경기 상태 변경 이벤트는 DB 저장 성공 뒤에만 메모리 상태, sequence와 방송을
  확정한다 (`docs/00`, `spec/turn_state_machine.yaml`의
  `game_state_event_commit_order`, ADR-0002).
- 진행 중 경기 이벤트는 감사 로그로 저장한다. v1은 이를 재시작 복구에 쓰지 않지만,
  같은 프로세스 수명 안에서 재접속 snapshot + 누락 이벤트 번들(ADR-0009)과 멱등
  결과 재전송의 event sequence 범위 읽기(ADR-0002)는 개별 이벤트 조회를 요구한다.
- 서버 이벤트 순서는 방 생명주기 단위 1부터의 연속값이다 (ADR-0007).
- 채팅은 같은 방 sequence 공간을 공유하는 부가 기능이며, 저우선순위 비차단 저장
  경로(ADR-0001)와 재접속 시 이전 기록 비복구(ADR-0010) 제약을 받는다.
- v1 데이터베이스는 단일 writer SQLite WAL이다 (ADR-0001).

## 평가

판정 기준은 `docs/12`가 고른 것 그대로다: 상태 확정 전 저장 계약, 멱등 재전송,
감사 가능성, 경기 기록 조회 비용, 스키마 버전 변경과 SQLite 인덱스 비용.

선택지 2는 기각한다. 턴·경기 단위 배치 저장은 이벤트별 "저장 성공 뒤 상태 확정"
계약과 충돌한다. 부분 실패 시 어느 이벤트까지 확정되었는지 모호해져 자동 정지·무효
판정이 불명확해진다. 재접속 번들이 개별 sequence 이벤트를 요구하므로 결국 해체
저장이 필요해진다는 점에서도 이중 표현이 된다.

선택지 3은 현재 근거 없이 보류한다. 종료 시점 기보 복사본은 조회 비용 문제가 실제로
관측된 뒤 추가할 수 있는 파생물이며, 지금 두면 두 저장소의 일치를 유지하는 쓰기
경로만 먼저 늘어난다. 전적·게임 로그(Milestone 5) 구현 시점에 조회 부하 근거가
확인되면 별도 ADR로 도입을 다시 판단한다.

## 결정

선택지 1을 채택한다. 방 sequence별 typed event 행을 경기 이벤트의 유일한 정본
저장으로 삼는다.

- 한 확정 이벤트는 한 행이다. 자연키는 `(room_id, sequence)` UNIQUE다. `room_id`는
  한 방 생명주기를 식별하고 `sequence`는 ADR-0007의 방 단위 연속값이다.
- 각 행은 이벤트 타입 식별자, 스키마 검증을 통과한 구조화 JSON payload와 함께
  작성 시점의 `schema_version`을 기록한다. payload 계약의 정본은 v1 스키마
  파일(`schemas/ws_server_event.schema.json` 등)이고, 스키마 변경은 새 버전을
  추가하는 방식으로만 한다.
- 저장 커밋 순서는 `game_state_event_commit_order`를 따른다. persist_event가
  성공하기 전에는 메모리 상태, sequence와 방송을 확정하지 않는다. 저장 실패 시
  자동 정지·재시도·무효 처리는 ADR-0002와 `spec/turn_state_machine.yaml`의
  persistence 계약 그대로다.
- 멱등 재전송과 재접속 동기화는 `(room_id, sequence)` 범위 스캔으로 충족한다.
  PRIMARY KEY `(room_id, sequence)`가 이 스캔을 커버하므로 다른 보조 인덱스를
  두지 않는다. 추가 인덱스는 조회 요구가 부하 시험이나 실제 쿼리로 입증될 때
  별도 ADR로 추가한다.
- 채팅 이벤트도 같은 테이블과 같은 방 sequence 공간에 적지만 ADR-0001의
  저우선순위 비차단 경로로 쓴다. 채팅 저장 실패는 경기와 채팅 전달을 중단하지
  않는다 (ADR-0002). 재접속 번들은 ADR-0010대로 채팅을 복구하지 않는다.
- 사람이 읽는 기보(`{윷 결과}{[말 ID][이동 전 위치][이동 후 위치]}` 압축 표기)는
  저장 계약이 아니라 이벤트 행에서 파생하는 조회 표현이다. v1은 종료 시점 기보
  생성을 두지 않고 조회 시점 파생을 사용한다.

## 결과

- "DB 저장 성공 뒤 상태 확정" 원칙이 저장 형태와 직접 일치한다. 이벤트 한 건의
  내구성과 상태 확정이 같은 트랜잭션 경계 안에 있다.
- 감사 로그가 손실 없는 typed event로 남는다. 결과 큐, 업기·잡기, CPU 선택,
  연결 상태, 시간 초과, 일시 정지, 승패와 무효 사유를 모두 payload로 보존한다.
- 재접속 누락 이벤트 번들과 멱등 범위 재전송이 하나의 인덱스로 해결된다. SQLite
  단일 writer 환경에서 쓰기 경로와 인덱스 유지 비용이 최소화된다.
- 기보 조회는 v1에서 이벤트 스캔 비용을 치른다. 경기 길이가 짧고 동시 접속 목표가
  작아(ADR-0001) 허용 가능한 예측이지만, Milestone 5에서 조회 비용을 측정해야
  하며 임계를 넘으면 선택지 3형 파생 테이블 ADR로 후속한다.
- 이벤트 payload 스키마가 진화하면 행별 `schema_version`과 파생 코드가 구버전
  payload를 계속 읽을 수 있어야 한다. 이는 리더 구현의 필수 조건이다.
